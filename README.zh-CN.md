# Hermes Memory Skills

[English](README.md) · **中文**

给 [Hermes Agent](https://hermes-agent.nousresearch.com/docs) 用的记忆技能对：让长期记忆**保持少量且诚实**，而不是一路涨到写不进去。

> 这是一个**技能仓库**，不是插件，也不是记忆后端。它只提供两个 `SKILL.md` 和一行配置，不碰 Hermes 内部，也不提供自动清理——上游把记忆溢出当作预期行为，不是 bug。

---

## 它解决什么

Hermes 每轮把 `MEMORY.md` 和 `USER.md` 注入 system prompt。由此产生三个后果，默认全都没人管：

1. **写进去的每个字都永久付费。**「阶段 3 完成」「试了端口 8080 通了」这类东西，会在之后整年的每一条消息里占着位置。
2. **没人判断它该不该在那儿。**一次性调试细节和机器级硬约束，写下来之后长得一模一样。
3. **满了就是满了。**没有自动压缩。写入开始被拒，而你是在任务做到一半时才知道。

记忆质量不是体积问题，是**路由**问题。这两个技能处理的就是路由。

---

## 改变什么

| | 之前 | 之后 |
|---|---|---|
| **写入时** | agent 觉得值得记就记 | 三道门 + 四问决定：**存不存、归哪层、怎么加载** |
| **记忆将满** | 写入被拒了才发现 | 80% 提醒；95% 不腾空间不许写 |
| **存量整理** | 临时手动删，风险是删掉来之不易的约束 | 路由：每条事实移到最小的正确归宿。删除是最后手段，且要过审批 |

两个技能，两种职责：

- **`memory-write-discipline`** —— 写入**之前**跑。价值门 → 归属/作用域门 → 加载成本门。回答「这条配不配存在，存在哪里」。
- **`memory-cleanup`** —— 存量**已经臃肿**时跑。盘点 → 搬迁计划 → 提案文件 → 核对清单 → 应用。默认 dry-run，必须人审批。

两者靠一个容量阈值连起来：写入很便宜，所以要在上面装个闸。

---

## discipline 的作用范围（先读这段）

**它给写记忆规定了一套规则，但 Hermes 的写入不受这套规则强制控制。**

`memory()` 调用链上没有任何代码会加载技能——写入前加载 discipline 完全靠模型自愿，只有当会话话题恰好和记忆/环境相关时才可能发生。实测结论：

| 写入来源 | 受 discipline 约束吗 |
|---|---|
| 你在对话里要求「记一下 X」 | 概率性——话题相关才可能加载 |
| agent 干活途中顺手写一条 | **基本不受**——「顺手写」恰恰不会先去 skill_view |
| 后台 fork 的自动提案 | **完全不受**——fork 看不到技能机制 |

所以 discipline 的真实定位是**写入质量的参考**（该不该存、归哪层、怎么写），不是写入闸门。别把它当成「装了就干净」的方案。

---

## MEMORY 的两种维护方式

既然写入侧无法强制，治理只能靠维护策略。两条路线：

**路线 A：任由写入 + cleanup 事后筛（作者采用）**

- 平时任 `memory()` 写，纪律靠 discipline 提高写入质量（概率性）
- 80% 黄线是**硬触发**：`memory()` 返回 `current/limit` ≥ 80% 时，agent 必须当轮提醒并建议跑 cleanup dry-run
- 坏条目的代价是「窗口期污染」：cleanup 两次运行之间，坏条目一直占每轮注入预算。写入频率低、水位低时代价很小

**路线 B：每次写入都审核（`memory.write_approval: true`）**

- 机制上真正强制：所有 memory/skills 写入进 pending 目录等人批
- 代价：审核被推迟到你**没有当场上下文**的时候——隔天批量批准的质量最差；定时/后台任务的写入会积压

**取舍一句话**：路线 B 的问题不是审核本身，而是审核时机。写入频率不高就选 A，把黄线当硬闸；discipline 不删——它的规则文本就是将来想做「pending + 脚本语义审」强制链路时的 prompt 规则源。

## 内容

### `memory-write-discipline` —— 原创

纪律层。就算你不打算安装，有四段值得读：

- **§1 三道门。** 价值 / 作用域 / 加载。最关键的一条：**不能用后一道门去否决前一道门**——「不值得每轮付费」不能毙掉一条本来就该待在作用域文件里的事实。
- **§3 过滤四问。** 价值、可推导性、重复、成本。负面清单（PR 号、SHA、临时路径、任务进度）是这四问的实例，不是另外 12 条规则。
- **§4 写法。** 陈述句，不祈使句。`用户偏好简洁回复` ✓ / `永远简洁回复` ✗——祈使句会被当成现行指令重读，可能盖过用户刚刚说的需求。
- **§5 工具机制。** `patch` 替换的是 **span**，不是整条。只传开头一句，旧尾巴会留着——文件越改越长，而调用照样返回 success。

还写了**日期标签**策略，以及为什么默认**不加日期**：时间戳只提供一个信号，却会破坏 `patch` 寻址、制造精确去重挡不住的重复；决定性的一条是——它容易诱使下游代码把**年龄当陈旧**，而对越老越珍贵的硬约束来说，这个方向恰好是反的。

### `memory-cleanup` —— fork

TechNickAI 的 `memory-cleanup` v0.1.2 的 MIT fork。它的核心原则值得原样引用：*「This is not a deletion pass. It is a routing pass.」*

保留为**冻结 fork，不追上游**——上游已不再提供这个文件。三处本地适配记录在 [`THIRD-PARTY.md`](THIRD-PARTY.md)，没有删除任何原始条款。

## 安装

**1. 取技能**

```bash
git clone https://github.com/Loo1015/hermes-memory-skills.git
cp -r hermes-memory-skills/skills/memory-write-discipline <SKILLS_DIR>/
cp -r hermes-memory-skills/skills/memory-cleanup           <SKILLS_DIR>/
```

`<SKILLS_DIR>` 用 `hermes config get skills_dir` 查，常见是 `~/.hermes/skills/`。**别照抄任何人机器上的绝对路径，包括作者的。**

确认：

```bash
hermes skills list | grep memory
```

两行都应是 `enabled`。

**2. 核对上限**

```bash
hermes config get memory.memory_char_limit   # 默认 6000
hermes config get memory.user_char_limit     # 默认 4000
```

**3. 知道技能不会自己生效**

技能**不是确定性通道**。模型按 description 自行决定要不要加载，没有强制触发机制，所以两个 `SKILL.md` 装好后只是躺在硬盘上的说明书——什么时候被读取决于会话话题。

这一点不靠往 `SOUL.md` 里塞提示词来补救：那样做只是把「提醒模型加载技能」变成又一条每轮付费、且同样不保证执行的文字。要真正的机制保证，只有改源码挂钩子或走 `memory.write_approval`（见上面「两种维护方式」的路线 B）；判断标准是这条规则漏一次会怎样，而不是它出现的频率。

**4. 可选的首次运行**

在会话里跟你的 agent 说：

> 用 memory-cleanup 对我的 MEMORY.md 和 USER.md 做一次 dry-run，产出核对产物，先别改。

你会拿到盘点表、搬迁计划、提案文件、核对清单。你批准之前什么都不会写——这个闸是技能自带的。

## 阈值

按比例算，跟着你的配置走，不写死数字：

| 占用 | 行为 |
|---|---|
| < 80% | 不管 |
| ≥ 80%（黄线） | 回复末尾一行：哪一层 / 字符数 / 百分比 / 建议 |
| ≥ 95%（红线） | 提醒 + 下次写入前**必须**在同一个原子 batch 里腾出等量空间 |

这两个数字是**本项目自己的操作阈值，不是平台行为**。Hermes 只在 100% 处硬拦（且检查整个 batch 的最终值）。80/95 存在的理由是：你希望在还有余裕思考的时候开始压缩，而不是在写入已被拒的时候。

## 已知的坑

以下都是实测观察到的，不是推演：

1. **`memory()` 只有 `add` / `patch` / `remove`，没有 `replace`。** 调 `replace` 会报错并指向 `patch`。
2. **`patch` 替换的是 span。** `old_text` 只给一部分 → 旧尾巴留着，条目变长，而且返回 success。重写整条必须把**完整条目**作为 `old_text`。
3. **只有精确去重，没有语义去重。** `Voce Rick speed 1.55` 和 `voce rick velocità 1.55` 是两条。写入前得自己找近似重复。
4. **写入立刻落盘，但下个会话才进 system prompt。** 记忆是冻结快照，当轮读不回自己刚写的东西。
5. **按字符计，不按字节。** 中文为主的记忆文件字节数约是字符数的 3 倍。用工具回报的 `current/limit`，别用 `os.path.getsize`。
6. **别用后台提案批量改记忆。** 无 shell 的 fork 只能写、不能验证；已观察到自动生成的记忆修改会写坏内容。必须人在环。
7. **指针不等于交付。**「它在 Hindsight 里」只证明内容已存储且可检索，不证明 prefetch 会在需要时把它捞上来。
8. **凭会话快照写 `patch` 的 `old_text` 会失败。** 记忆以会话开始时的冻结快照注入，中途写入只落盘不改快照——文件可能已经变了。patch 前必须读磁盘，不能凭对话里早先引用过的版本。（实测：一次 3 操作的原子 batch 因此整体回滚，原子性挡住了半成品状态。）
9. **黄线提醒只在 `memory()` 写入后检查。** 整轮会话不写记忆，水位涨了也不会有人提。后台 fork 的写入不经过这个检查点，完全不触发。想主动查水位，用 `hermes memory status` 或直接问 agent。
10. **`patch` 的 `old_text` 要和磁盘条目逐字一致。** 想改的事实可能根本不是独立条目，而是混在别的条目里——按记忆里的印象写 `old_text` 大概率匹配失败。

---

## 什么情况下不该用

- 你希望记忆自由生长、偏好检索而非治理——用一个记忆后端（Hindsight、Mem0 等），两个技能都不用装。
- 临时 profile，或者记忆文件本来就又小又新。
- 你期待自动化。两个技能都不会自动清理记忆，都得明确调用。
